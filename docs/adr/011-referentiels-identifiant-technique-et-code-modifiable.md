# ADR-011 : Référentiels, identifiant technique et code modifiable

- Statut : accepté ; amendé le 2026-10-08 (auteur d'une action, identifiants `bigint` confirmés) le
  2026-10-14 (références opaques de `facturation`) et le 2026-10-17 (objet d'une conversation)
- Date : 2026-10-06
- Remplace : la « référence par code métier » de l'ADR-008 (décision A-REF-1 de la spec 01)
- Spec : `docs/specs/01-referentiels/spec.md` (A-REF-1, RG-REF-02, RG-REF-04)

## Contexte
L'ADR-008 faisait référencer les valeurs de référentiel par leur code métier, rendu immuable
(RG-REF-02, H-REF-4) : une erreur de code ne pouvait se corriger qu'en désactivant la valeur et en
en créant une autre, et aucune valeur ne pouvait être supprimée (RG-REF-04).

À l'usage des premiers écrans, ces contraintes se révèlent trop rigides : l'erreur de saisie est
courante, il faut pouvoir revenir sur ce que l'on a fait, et elles desservent la démonstration
(décision du 2026-10-06).

## Décision
- **Identifiant technique.** Chaque valeur de référentiel (les treize listes, contenances et classes
  de TVA comprises) a un identifiant entier, généré par PostgreSQL (`bigint generated by default as
  identity`). Les autres contextes stockent cet identifiant (`pays_id`), avec une clé étrangère vers la
  table de `referentiels`. Les URL de l'API le portent (`/api/referentiels/pays/42`).
- **Code modifiable.** Le code (le volume pour une contenance) se corrige comme le libellé. Il reste
  obligatoire et unique dans sa liste, sans distinction de casse (RG-REF-01).
- **Suppression si inutilisée.** Une valeur que rien ne référence se supprime. Si une autre donnée y
  fait référence, la clé étrangère refuse la suppression : l'API répond 409 (`ElementUtilise`,
  RG-REF-04) et la valeur se désactive à la place.
- **Lecture publiée par identifiant et par code.** `ReferentielsLecture` (ADR-008) offre, pour chaque
  liste, la lecture par identifiant (affichage d'une valeur référencée), par code (imports et reprise,
  dont les fichiers portent des codes) et des valeurs actives. Les vues publiées exposent l'identifiant
  et le code.

Options écartées :
- garder la référence par code, en propageant chaque changement de code aux autres contextes : une
  écriture dans tous les contextes consommateurs, contraire à leur isolement ;
- un UUID : généré sans aller-retour en base, mais illisible dans les URL et au débogage, sans gain
  pour un prototype à une seule base ;
- garder le volume comme identifiant de la contenance : incohérent avec les autres référentiels, et
  une erreur de saisie (0,07 au lieu de 0,70) resterait incorrigeable ;
- la suppression libre : une valeur utilisée ailleurs laisserait des références orphelines.

## Conséquences
- La partie publiée de l'ADR-008 est inchangée dans son principe (packages `partage`, lecture seule) ;
  seules ses méthodes et ses vues changent.
- La reprise AGI traduit chaque code AGI en identifiant, par la lecture par code.
- Les imports (ventes export, DSM) traduisent les codes des fichiers en identifiants de la même façon.
- Un code peut changer : un contexte qui affiche un code le relit par l'identifiant, il ne le recopie
  pas.
- Chaque contexte consommateur déclare une clé étrangère vers la table du référentiel qu'il utilise :
  c'est elle qui protège une valeur utilisée contre la suppression.

## Amendement du 2026-10-08 (spec 03, spec 02 révisée)
- **Identifiants `bigint` confirmés** pour tous les objets, y compris les personnes et les accès de
  `operateurs` et le compte de connexion de `authentification` (A-AUT-4, A-OPE-9). Le principe
  « identifiants UUID » de la vision du 2026-10-08 n'est pas suivi : l'e-mail n'étant jamais un
  identifiant, son objet est atteint ; l'UUID reste écarté pour les mêmes raisons qu'en 2026-10-06.
- **Exception : l'auteur d'une action.** Un utilisateur est supprimé quand il perd son dernier
  rattachement (ADR-016). Un contexte qui enregistre l'auteur d'une action (DSM « saisie par », contrat
  « validé par », suivi export « créé par »…) stocke donc son identifiant **sans clé étrangère**, avec une
  copie de son nom à l'instant de l'action (A-OPE-8). Les journaux font de même.
- **Exception : `authentification`.** Le compte de connexion référence l'utilisateur sans clé étrangère ;
  la cohérence passe par les événements de `operateurs` (ADR-015).
- Écartés : ne jamais supprimer un utilisateur (comptes dormants, écart à la vision) ; bloquer la
  suppression d'un utilisateur auteur d'une action (deux comportements selon l'historique).

## Amendement du 2026-10-14 (spec 08, décision A-FAC-8)
- **Exception : les références opaques de `facturation`.** `facturation` est une lib en aval (ADR-021) :
  elle ne connaît pas les tables de ses sources, ni celles de son hôte. L'origine d'une facture
  (`Origine` : source, nature, identifiant de l'objet chez la source) et son client (`ClientRef` :
  identifiant et code de l'opérateur) sont donc stockés en texte, **sans clé étrangère**. Des index sur
  (source, identifiant) et sur le client portent l'unicité d'une facture vivante par origine et les
  recherches.
- La facture recopie tout l'acheteur. Supprimer un opérateur ne la rend pas incohérente :
  `facturation` ne protège pas l'opérateur facturé contre la suppression.
- Écartée : une clé étrangère par source (une colonne par type d'objet), qui ferait dépendre la lib de
  chacune de ses sources.

## Amendement du 2026-10-17 (spec 15, décision A-MSG-5)
- **Exception : l'objet d'une conversation.** `messagerie` est une lib en aval (ADR-023) : l'objet métier
  d'une conversation (`ObjetMetier` : type, identifiant de l'objet chez son contexte, libellé copié) est
  stocké en texte, **sans clé étrangère** ; un index unique sur (type, identifiant) porte l'unicité d'une
  conversation par objet. Le contexte de l'objet supprime la conversation avec lui (`Conversations`).
- L'opérateur d'une conversation garde, lui, sa clé étrangère : `messagerie` dépend d'`operateurs`, et un
  opérateur qui a des conversations ne se supprime pas, comme avec ses DSM.
- Écartée : une clé étrangère par type d'objet, qui ferait dépendre la lib de chaque contexte métier.
